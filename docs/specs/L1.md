# L1 - High-Level Requirements

Keryx is a news aggregator for everything Christian and fitness, primarily in Toronto and the
Greater Toronto Area and also around the world. Workers collect what organizations publish,
an API serves it to other products (Christian Fitness is the first), and a staff-only admin app
watches the collection and curates the result. Keryx has no public website of its own.

These requirements describe the whole product. Their inputs are the mocks in
[`docs/mocks/`](../mocks/README.md) (what staff see and do), the engineering rules in
[`AGENTS.md`](../../AGENTS.md) (how the system must behave and be built) and the design system in
[`docs/design-system/`](../design-system/README.md). Detailed, testable behaviour is in
[L2.md](L2.md); decisions these documents made where the inputs disagreed or were silent are
listed at the end of L2.

## L1-001: Source catalogue
Staff must be able to keep the list of places Keryx collects from: add a source, test it, edit
it, remove it and see the health of each one. A source is a feed, a web page, a social account,
an event organizer or a news query, belonging to an organization and a region.

## L1-002: Scheduled and on-demand collection
Workers must collect from every source on a schedule staff control, and when staff ask, without
a person watching. A collection moves through fixed stages (fetch, parse, classify, deduplicate,
store, publish), and one source failing must not stop the others.

## L1-003: Ingestion integrity and provenance
Collecting the same thing twice must change nothing. Every record must have a stable identity,
the same item found through two sources must be one record, and every stored fact must carry
where it came from, its link, and when it was first and last seen.

## L1-004: Relevance and publication
Keryx must score each collected item for Christian-fitness and geographic relevance, publish
what scores high, hold what is uncertain for staff review, hide the rest, and let staff overrule
any of those decisions. Only published records are served to other products.

## L1-005: The record catalogue
Keryx must hold articles (news), events and organizations (including churches), each carrying
where it is and, where it has a time, that time in UTC with its zone. Toronto and the GTA come
first.

## L1-006: Run recording
Every run of every worker must be recorded: which worker, what started it, when it started and
finished, its outcome, the result of each stage and each source, and how many records it added,
updated and left unchanged. Problems found in a run must be kept as issues staff can act on.

## L1-007: Respectful and safe fetching
Keryx must be a good citizen of each source (honour `robots.txt` and terms of use, identify
itself, rate-limit, back off, time out) and must treat everything it fetches as untrusted input:
validated, bounded, never executed, never followed to a private or internal address.

## L1-008: The consumer API
Other products must be able to read published articles, events, organizations, categories,
regions and collection freshness through a versioned, documented HTTP API whose lists are paged
and bounded and whose contract is never broken in place.

## L1-009: API clients and keys
Each consuming product must authenticate with its own API key carrying only the scopes it
needs. Staff must be able to create a key, see it exactly once, revoke it, and see how each
product uses the API. Clients must be rate-limited.

## L1-010: Staff authentication and authorization
Only signed-in staff can use the admin app and the admin endpoints. Every endpoint must require
authentication unless it is explicitly anonymous, and a signed-in person who is not staff must
be refused.

## L1-011: Admin shell and Overview
The admin app must give staff one consistent frame (navigation, the next collection, who is
signed in) and an Overview that answers at a glance: did the last run work, what did it bring
in, what needs attention, and when is the next one.

## L1-012: Article review
Staff must be able to browse, search and filter everything Keryx has collected, open one
article with its provenance and relevance, publish it or hide it from the API, undo that, and
export the list.

## L1-013: Run history
Staff must be able to see every run, which ones had problems, what happened at each stage of a
run, the issues it raised, and must be able to start a run, retry what failed and mute an issue.

## L1-014: Source management screen
Staff must be able to see every source with its health, region, yield and last fetch, filter
the list by kind, and reach add, edit, test and remove from it.

## L1-015: API management screen
Staff must be able to see the API's base address, traffic, latency and error rate, each
consumer with its key and usage, and the endpoints with an example of each.

## L1-016: Settings
Staff must be able to change how Keryx collects, scores, places, stores and alerts (schedule,
timeout, topics, exclusions, thresholds, focus areas, retention, alert rules) with validation,
an explicit save and no silent loss of unsaved changes.

## L1-017: Feedback, states and notifications
Every screen and dialog must show a designed state for loading, empty, error, no results,
invalid input, busy and success, and every action must report its outcome through a
notification, with Undo where the action can be reversed.

## L1-018: Operational alerts
Keryx must tell the people who run it when a source keeps failing, when a whole run fails, and,
if they choose, send a daily digest of articles waiting for review.

## L1-019: Privacy and source respect
Keryx aggregates what organizations publish. It must store facts and a link, not a copy of a
source's article; must not collect private individuals' contact details; must show a named
person only as the source published them; and must not keep records longer than staff decide.

## L1-020: Security
The system must protect itself, its data, its sources and its consumers against the OWASP Top
10: authentication and authorization on every endpoint, validated input, safe output, protected
secrets, safe outbound requests, and errors that reveal nothing useful to an attacker.

## L1-021: Performance and efficiency
The API must answer quickly under load, collection must finish well inside its interval, and
the admin app must load only what it needs and stay as smooth after an hour on a low-power
device as at the start.

## L1-022: Responsive design and accessibility
The admin app must work at every viewport from a phone to a wide desktop, by touch and by
keyboard, in light and dark themes, and must meet WCAG 2.2 level AA.

## L1-023: Observability and operations
The system must be observable through OpenTelemetry without leaking private data, must report
its health, must change its database only through an explicit command, and every setting a
deployment needs must be documented.

## L1-024: Brand and design system
The admin app must look and behave as the mocks and the design system define: the Keryx mark
and wordmark, its own favicon, design tokens read by role, one component per design-system
component, and bundled fonts.
