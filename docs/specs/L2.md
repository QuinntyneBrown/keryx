# L2 - Detailed Requirements

Each requirement traces to exactly one [L1](L1.md) and has acceptance criteria in
Given/When/Then form, written so that an acceptance test can be taken from them directly.
Screens, dialogs and notifications named here are the mocks in
[`docs/mocks/`](../mocks/README.md); "the mock" always means the mock of that screen and state.

**Conventions used throughout**

- *Staff* is a signed-in person who passes the staff policy. *Client* is a consuming product
  calling with an API key. *Now* is read from `TimeProvider`.
- The consumer API lives under `/v1`; the admin endpoints the admin app calls live under
  `/admin/v1`. JSON property names are `snake_case`. Times are ISO 8601 with an offset.
- Errors are RFC 9457 ProblemDetails. Where a caller branches on an error it carries a `code`
  extension; the codes are named in the criteria.
- Counts, durations, scores and rates are served as numbers. The admin app formats them.
- Every acceptance test file starts with a comment naming the L2 requirements it covers:

  ```csharp
  // Acceptance Test
  // Traces to: L2-009, L2-011
  // Description: A second run against an unchanged fake source adds and updates nothing
  ```

  ```typescript
  // Acceptance Test
  // Traces to: L2-058
  // Description: Publishing a held article moves it to Published and offers Undo
  ```

## L2-001: Source record
**Traces to:** L1-001

A source has a kind (`rss`, `website`, `instagram`, `eventbrite`, `news_query`), an address
(a URL, or for a news query the query text), the organization it belongs to, a region, a
health, and the times it was created, last fetched and last succeeded.

**Acceptance Criteria:**
1. Given a staff request to create a source with kind `rss`, a valid `https` URL, an organization name of 1 to 120 characters and a known region, when it is sent, then the response is `201` with the source's id, and a later `GET /admin/v1/sources/{id}` returns the same values.
2. Given a create request whose URL does not start with `http://` or `https://`, whose organization name is empty, or whose region is unknown, when it is sent, then the response is `400` with `code` `validation_failed` and an `errors` entry for each failing field, and nothing is stored.
3. Given a source with the same kind and the same normalized address already exists, when a create request for it is sent, then the response is `409` with `code` `source_exists` and nothing is stored.
4. Given a URL that differs from an existing one only by scheme case, host case, a trailing slash or a fragment, when it is normalized, then it equals the existing one.
5. Given a create request with kind `news_query` from the admin app, when it is sent, then the response is `400` with `code` `kind_not_creatable`; news query sources are created by seed data only.

## L2-002: Source test fetch
**Traces to:** L1-001

A source can be fetched once, outside a run, to tell staff whether it works and whether what it
returns looks relevant. A test fetch stores no records.

**Acceptance Criteria:**
1. Given a reachable source address whose items are scored, when `POST /admin/v1/sources/test` is sent with its kind and address, then the response is `200` with `items_found` and `items_relevant` as numbers, and no article, event, organization or run is created.
2. Given an address the source answers with an error or does not answer within the per-source timeout, when the test is sent, then the response is `200` with `reachable: false` and a `reason` from the fixed list `not_found`, `timeout`, `blocked_by_robots`, `refused`, `invalid_content`, `unsafe_address`.
3. Given an existing source, when `POST /admin/v1/sources/{id}/test` is sent, then the result is returned the same way and the source's stored health is not changed.
4. Given a test fetch, when it runs, then it obeys every rule of L2-021 to L2-024 (robots, rate limit, timeout, safe address).

## L2-003: Edit and remove a source
**Traces to:** L1-001

Staff must be able to change a source's address, organization and region, and remove a source,
without losing what was already collected from it.

**Acceptance Criteria:**
1. Given an existing source, when staff save a changed address, organization or region, then the response is `200`, the change applies from the next run, and the address is test-fetched once as part of saving with the result returned in the response.
2. Given an edit that would make the source equal to another existing source, when it is saved, then the response is `409` with `code` `source_exists` and nothing changes.
3. Given an existing source with collected articles, when staff remove it, then the response is `204`, the source is no longer fetched or listed, and every article, event and organization collected from it remains stored and served with its provenance unchanged.
4. Given a removed source, when the same kind and address are added again, then a source is created and items it yields match their existing records (no duplicates are created).
5. Given a source id that does not exist, when it is read, edited, tested or removed, then the response is `404` with `code` `source_not_found`.

## L2-004: Source health
**Traces to:** L1-001

A source's health is `healthy`, `needs_look` or `failing`, derived from its most recent
fetches, never typed by a person.

**Acceptance Criteria:**
1. Given a source whose last fetch succeeded and raised no warning, when it is read, then `health` is `healthy`.
2. Given a source whose last fetch failed, when it is read, then `health` is `failing`, with `failure_reason` from the fixed list of L2-002 and `consecutive_failures` as a number.
3. Given a source whose last fetch succeeded but had at least one item held for review, when it is read, then `health` is `needs_look` with `held_count` as a number.
4. Given a failing source, when its next fetch succeeds, then `health` becomes `healthy` or `needs_look` and `consecutive_failures` is `0`.
5. Given a source never fetched, when it is read, then `health` is `healthy`, `last_fetched_at` is `null` and `consecutive_failures` is `0`.

## L2-005: Collection schedule
**Traces to:** L1-002

The collection worker starts a run at fixed intervals aligned to midnight Toronto time. The
interval is one of 1, 3, 6, 12 or 24 hours (default 6) and comes from Settings.

**Acceptance Criteria:**
1. Given an interval of 6 hours and a fake clock at 05:59:59 Toronto time, when the clock is advanced by one second, then exactly one scheduled run starts.
2. Given an interval of 6 hours, when the next run time is read at 09:46 Toronto time, then it is 12:00 the same day, and `next_run_at` is served in UTC with zone `America/Toronto`.
3. Given the interval is changed from 6 to 3 hours and saved at 09:46, when the next run time is read, then it is 12:00, and the one after is 15:00.
4. Given a day on which Toronto's clocks change, when the schedule is advanced through it, then runs start at the wall-clock times of the interval and none is skipped or doubled.
5. Given a scheduled time arrives while a run is still in progress, when the schedule fires, then no second run starts, the skipped start is recorded as an issue on the running run, and the next run starts at the following scheduled time.
6. Given any schedule decision, when the code reads the time, then it reads `TimeProvider`; a test proves each case by advancing `FakeTimeProvider`, never by sleeping.

## L2-006: Run on demand
**Traces to:** L1-002

Staff must be able to start a collection run at any time; at most one collection run is in
progress at once.

**Acceptance Criteria:**
1. Given no run is in progress, when staff send `POST /admin/v1/runs`, then the response is `202` with the new run's id, its `trigger` is `manual`, and the run proceeds as a scheduled one would.
2. Given a run is in progress, when staff send `POST /admin/v1/runs`, then the response is `409` with `code` `run_in_progress` and the id of the running run, and no run is created.
3. Given two requests to start a run arrive at the same time, when both are handled, then exactly one run is created.
4. Given a manual run finishes, when the next scheduled time is read, then it is unchanged by the manual run.

## L2-007: Collection pipeline stages
**Traces to:** L1-002

A collection run has six stages in this order: `fetch`, `parse`, `classify`, `deduplicate`,
`store`, `publish`. Each stage records a status (`not_run`, `running`, `done`,
`done_with_warnings`, `failed`), a duration and a count summary.

**Acceptance Criteria:**
1. Given a run in which every source answers, when it finishes, then all six stages are `done`, each with `duration_ms` as a number, and the run's outcome is `succeeded`.
2. Given a run in which 2 of 64 sources fail to fetch, when it finishes, then `fetch` is `done_with_warnings` with `sources_ok` 62 and `sources_failed` 2, the later stages process the items of the 62, and the run's outcome is `completed_with_issues`.
3. Given a run in which the `store` stage cannot reach the database, when it stops, then `store` is `failed` with a generic reason, every later stage is `not_run`, nothing from this run is served by the API, and the outcome is `failed`.
4. Given a run in which items are held for review, when it finishes, then `classify` is `done_with_warnings` and its summary gives `relevant`, `held` and `off_topic` as numbers that sum to the items parsed.
5. Given a failed run, when the API is read, then it serves exactly what it served before the run began.

## L2-008: Source isolation and retry within a run
**Traces to:** L1-002

One source failing must not stop a run: its failure is recorded, the other sources are
processed, and staff can fetch only the failed sources again.

**Acceptance Criteria:**
1. Given a fake source that throws on fetch and another that answers, when a run executes, then the second source's items are stored and the first is recorded as failed with its reason.
2. Given a source that times out, when it is fetched, then it is retried up to 3 times in total with increasing delay, and it is recorded as failed only after the last attempt.
3. Given a finished run with failed sources and no run in progress, when staff send `POST /admin/v1/runs/{id}/retry`, then only the failed sources are fetched again, their items pass through the remaining stages, the counts and issues of that same run are updated, and no new run is created.
4. Given a retry in which one of two failed sources answers, when it finishes, then the run's `sources_failed` is 1, the recovered source's issue is closed, and the outcome remains `completed_with_issues`.
5. Given a run whose outcome is `failed` at a stage, when staff send the retry request, then a new manual run starts and its id is returned.
6. Given the per-source timeout is 30 seconds, when a fake source delays past it on a fake clock, then the fetch is abandoned at 30 seconds.

## L2-009: Stable identity
**Traces to:** L1-003

Every record has an identity that does not depend on when it was collected: the source and the
item's key in that source (a feed GUID, a canonical URL, a platform id), or, where a source
gives no key, the normalized canonical URL.

**Acceptance Criteria:**
1. Given a fake source that returns the same 5 items on two consecutive runs, when the second run finishes, then it reports `added` 0, `updated` 0 and `unchanged` 5, and the articles table holds 5 articles.
2. Given an item whose title changes at the source between two runs, when the second run finishes, then it reports `updated` 1, the article keeps its id and first-seen time, and its last-seen time is the second run's.
3. Given an item returned with tracking parameters (`utm_*`, `fbclid`, `gclid`) or a fragment added to its URL, when it is collected again, then it matches the existing article.
4. Given public ids, when an article, run or source is created, then its id is prefixed `art_`, `run_` or `src_`, is never reused, and does not change for the life of the record.

## L2-010: Deduplication across sources
**Traces to:** L1-003

When merging is on (Settings, default on), an item that is the same story as an existing
article is merged into it: same canonical URL, or a headline whose normalized similarity to an
existing article of the same organization within 14 days is at least 0.90.

**Acceptance Criteria:**
1. Given an article collected from an organization's feed, when a news query source returns the same canonical URL, then no second article is created, the run counts it under `duplicates`, and the article lists both sources in its provenance.
2. Given the headline-similarity cases in the shared case table (identical; differing only in case, punctuation and whitespace; one word changed in ten; unrelated), when each is compared, then the first three merge and the last does not, with the threshold at exactly 0.90 inclusive.
3. Given merging is switched off in Settings, when two sources return the same story under different URLs, then two articles are stored; same-URL items still match by identity (L2-009).
4. Given the same event (same organization, same start time within 1 hour, same place) found through two sources, when both are collected, then one event exists listing both sources.
5. Given the same organization named through two sources with names that differ only in case, punctuation, whitespace or a leading "The", when both are collected, then one organization exists.

## L2-011: Provenance
**Traces to:** L1-003

Every stored record carries where each of its facts came from; an item with no identifiable
source or URL is not stored.

**Acceptance Criteria:**
1. Given any stored article, event or organization, when it is read through the admin endpoints, then it carries at least one provenance entry with the source id, the source's name, the URL the fact was read from, `first_seen_at` and `last_seen_at`.
2. Given a parsed item with no URL or from no identifiable source, when the store stage handles it, then it is not stored and is counted under `rejected` for the run.
3. Given an article collected again unchanged, when it is read, then `first_seen_at` is unchanged and `last_seen_at` is the later run's start time.
4. Given a source is removed, when its articles are read, then their provenance still names that source and its URL.

## L2-012: Relevance scoring
**Traces to:** L1-004

Each item gets a relevance score from 0.00 to 1.00, to two decimal places, from the topics, the
exclusions and the geography in Settings. The scoring rule is deterministic: the same item and
the same settings always give the same score.

**Acceptance Criteria:**
1. Given the scoring case table (an item matching several topics in a focus area; one matching topics outside every focus area; one matching an exclusion; one matching no topic), when each is scored with the default settings, then the scores are in that descending order and the excluded and no-topic items score below 0.45.
2. Given the same item scored twice with unchanged settings, when the scores are compared, then they are equal.
3. Given an item outside the focus areas, when "Ontario-wide organisations" is on and the item is in Ontario, then it scores higher than with that switch off.
4. Given a score computed as 0.585, when it is stored and served, then it is `0.59`; every score served is a number with at most two decimal places between 0 and 1 inclusive.
5. Given Settings change, when the next run scores new items, then the new settings apply; scores of articles already stored are not recomputed.

## L2-013: Publication status from thresholds
**Traces to:** L1-004

An article's status is `published`, `needs_review` or `hidden`. On collection it is set from
its score: at or above the publish threshold *T* (Settings, default 0.60) it is published; from
the review floor 0.45 up to but not including *T* it needs review; below 0.45 it is hidden.

**Acceptance Criteria:**
1. Given *T* = 0.60 and the case table of scores 1.00, 0.60, 0.59, 0.45, 0.44, 0.00, when each is classified, then the statuses are published, published, needs review, needs review, hidden, hidden.
2. Given *T* = 0.40 (below the review floor), when scores 0.44, 0.40 and 0.39 are classified, then they are published, published and hidden, and no article is held.
3. Given *T* is changed from 0.60 to 0.65 and saved, when an existing published article has score 0.62, then its status is unchanged; only items collected afterwards use 0.65.
4. Given a held article, when it is read through the admin endpoints, then `status_reason` is `below_publish_threshold` and `threshold` is the *T* in force when it was collected.
5. Given this rule is computed in both stacks, when the frontend and backend suites run, then both use the same inline case table.

## L2-014: Staff decisions on an article
**Traces to:** L1-004

Staff can publish or hide any article whatever its score, undo that decision, and a later run
never overrides it.

**Acceptance Criteria:**
1. Given an article that needs review or is hidden, when staff send `POST /admin/v1/articles/{id}/publish`, then its status is `published`, `decided_by` is `staff`, and it is served by the consumer API on the next request.
2. Given an article that is published or needs review, when staff send `POST /admin/v1/articles/{id}/hide`, then its status is `hidden` and the consumer API no longer returns it in lists and answers `404` for its id.
3. Given an article staff have decided, when a later run collects it again with any score, then its status is unchanged.
4. Given a decision was made, when staff send `POST /admin/v1/articles/{id}/revert` with the previous status within the same session, then the article returns to that status and `decided_by` returns to its previous value.
5. Given an article already in the requested status, when the same decision is sent again, then the response is `200` and nothing changes (the action is idempotent).
6. Given an article id that does not exist, when any decision is sent, then the response is `404` with `code` `article_not_found`.

## L2-015: Article record
**Traces to:** L1-005

An article is a pointer to a story, not a copy of it: a title, a summary of at most 500
characters, the canonical link, the organization, a category, a region, tags, the time the
source published it, the time Keryx collected it, a relevance score and a status.

**Acceptance Criteria:**
1. Given a parsed item with a title of 300 characters and a body of 5,000, when it is stored, then the title is stored whole up to 300 characters, the summary is at most 500 characters ending on a word boundary, and no more of the body is stored.
2. Given a parsed item with no summary, when it is stored, then the summary is the first sentence of the item, bounded the same way.
3. Given a parsed item with no title, when it is stored, then its title is `null` and the admin app shows "Untitled post"; the consumer API never serves an article without a title.
4. Given a parsed item whose organization cannot be determined, when it is stored, then `organization` is `null` and the admin app shows "Unknown".
5. Given the categories `events`, `races-challenges`, `gyms-studios`, `ministry-programs`, `nutrition`, `faith-wellness`, when an item is classified, then it gets exactly one of them.
6. Given up to 30 tags of at most 40 characters each on an item, when it is stored, then they are stored lower-cased and de-duplicated, and any beyond 30 are dropped.

## L2-016: Event record
**Traces to:** L1-005

An event is something with a start time and a place: a race, a class, a camp, a service
project. It is extracted when a source publishes a start time; it belongs to an organization
and, where it came from a story, links to that article.

**Acceptance Criteria:**
1. Given a parsed item with a start time and a place, when it is stored, then an event is stored with `title`, `starts_at` in UTC, `time_zone` as an IANA zone, `place_name`, `region`, `organization`, `url` and provenance.
2. Given a source that publishes a local time with no zone, when the event is stored, then the zone is the region's zone (`America/Toronto` for every GTA region) and `starts_at` is that local time converted to UTC.
3. Given an event linked to an article, when that article is hidden, then the event is not served by the consumer API; when the article is published, it is.
4. Given an event with no linked article, when it is collected, then its status follows the same thresholds as L2-013 from its own score.
5. Given an event whose end time is before its start time, when it is parsed, then the end time is dropped and the event is stored with `ends_at` `null`.

## L2-017: Organization record
**Traces to:** L1-005

An organization is a church, ministry, gym, club, network or business that publishes Christian
fitness news. It has a name as it publishes it, a kind (`church`, `ministry`, `gym`, `club`,
`network`, `business`, `other`), a region, and its public website.

**Acceptance Criteria:**
1. Given a source is added for an organization name not yet known, when it is saved, then an organization with that name and the source's region is created; given the name is already known (by the match of L2-010), then the source is attached to the existing one.
2. Given an organization, when it is read through either API, then it carries `id` (prefixed `org_`), `name`, `kind`, `region`, `website_url` and `article_count` as a number.
3. Given an organization with no published article and no published event, when the consumer API lists organizations, then it is not listed.
4. Given an organization record, when it is stored, then it holds no personal e-mail address, personal phone number or home address (see L2-081).

## L2-018: Regions and time
**Traces to:** L1-005

Every record carries a region. Regions are a fixed list with a slug, a name, a zone and a
rank: the GTA municipalities first (Toronto first of all), then `gta`, `ontario`, `canada`,
`global`.

**Acceptance Criteria:**
1. Given the region list is read, when it is returned, then Toronto is first, each entry has `slug`, `name` and `time_zone`, and `global` is last.
2. Given an item whose place cannot be resolved, when it is stored, then its region is the source's region.
3. Given any stored time, when it is read from the database, then it is UTC; where a wall-clock time matters (events, the schedule) the IANA zone is stored beside it.
4. Given a focus area is added in Settings that is not yet a region, when Settings are saved, then it becomes a region with zone `America/Toronto` and a slug made from its name.

## L2-019: Run record
**Traces to:** L1-006

Every run of every worker is recorded with its trigger, times, outcome, stage results and
counts, whether it succeeds or fails.

**Acceptance Criteria:**
1. Given any worker run ends, however it ends, when `GET /admin/v1/runs/{id}` is read, then it returns `worker`, `trigger` (`schedule` or `manual`), `started_at`, `finished_at`, `duration_ms`, `outcome` (`succeeded`, `completed_with_issues`, `failed`) and the counts `added`, `updated`, `unchanged`, `duplicates`, `held`, `off_topic`, `rejected`, `sources_ok`, `sources_failed`, every one a number.
2. Given a run is in progress, when it is read, then `outcome` is `running`, `finished_at` is `null`, and `sources_checked` and `sources_total` are numbers that advance as sources finish.
3. Given a worker throws an unhandled exception, when the host catches it, then the run is recorded as `failed` with a generic reason and a correlation id, and the worker's next scheduled run still starts.
4. Given three workers (`collection`, `retention`, `alert_digest`), when one fails, then the others run at their own times unaffected.
5. Given the process stops while a run is in progress, when the worker next starts, then that run is recorded as `failed` with reason `interrupted` before any new run begins.
6. Given the collection run of the mocks, when it is read, then `added` is 47, `duplicates` is 18, `sources_ok` is 62 and `sources_failed` is 2.

## L2-020: Run issues and muting
**Traces to:** L1-006

A problem found during a run is an issue: a severity (`error`, `warning`), a kind
(`source_not_found`, `source_timeout`, `source_blocked`, `source_invalid`, `items_held`,
`stage_failed`, `run_skipped`), the source or stage it concerns, a short detail, and how many
runs in a row it has occurred.

**Acceptance Criteria:**
1. Given a source fails with the same kind on 4 consecutive runs, when the issue is read, then `consecutive_runs` is 4 and `since` is the time of the first of them.
2. Given an open issue, when staff send `POST /admin/v1/issues/{id}/mute`, then it is no longer counted as open, no longer raises alerts (L2-077), and is still listed on its run with `muted: true`.
3. Given a muted issue, when staff send `POST /admin/v1/issues/{id}/unmute`, then it is open again.
4. Given a muted issue for a source, when that source's next fetch succeeds without that problem, then the issue is closed and the mute is cleared, so a later recurrence is a new open issue.
5. Given an issue's detail contains text from a source or an exception, when it is stored, then it is bounded to 300 characters and holds no query string, credential, internal host name or IP address.
6. Given open issues exist, when `GET /admin/v1/issues?state=open` is read, then errors come before warnings and, within a severity, the longest-running first; the list is paged.

## L2-021: Robots, terms and identification
**Traces to:** L1-007

Keryx must obey each site's `robots.txt` and each platform's terms, and identify itself on every
request.

**Acceptance Criteria:**
1. Given a site whose `robots.txt` disallows a path for Keryx's user agent or for `*`, when a source at that path is fetched, then no request is made to the path and the source fails with reason `blocked_by_robots`.
2. Given a site's `robots.txt` was fetched less than 24 hours ago, when another of its pages is fetched, then the cached copy is used; given `robots.txt` cannot be fetched (5xx or timeout), then the site is not fetched in this run.
3. Given any outbound request, when it is sent, then its `User-Agent` names Keryx, its version and a contact URL from configuration.
4. Given an `instagram` or `eventbrite` source, when it is fetched, then it is read only through that platform's official API with credentials from configuration; given no credentials are configured, then the source fails with reason `refused`, no scraping is attempted, and the add-source test reports the kind as unavailable.
5. Given a `Crawl-delay` in `robots.txt`, when the site is fetched, then successive requests to it are at least that far apart, up to a cap of 30 seconds.

## L2-022: Rate limiting, back-off and time-outs
**Traces to:** L1-007

Keryx must never overload a source: requests to one host are serialized and spaced, retries back
off, and every call has a time-out.

**Acceptance Criteria:**
1. Given several sources on one host, when a run fetches them, then at most 1 request is in flight to that host at a time and successive requests are at least 1 second apart.
2. Given a host answers `429` or `503` with `Retry-After`, when the fetch is retried, then it waits at least that long (capped at 60 seconds), and exponentially longer on each further attempt.
3. Given the per-source timeout from Settings (5 to 120 seconds, default 30), when a source does not complete within it, then the call is cancelled and counted as an attempt.
4. Given a run over 64 sources on a fake clock, when it executes, then no call is made without a timeout and at most 8 hosts are fetched concurrently.
5. Given a conditional request is possible (`ETag` or `Last-Modified` from the last fetch), when the source is fetched, then the request is conditional and a `304` counts as a successful fetch with no items.

## L2-023: Fetched content is untrusted
**Traces to:** L1-007

Everything fetched is untrusted input: it is bounded in size and count, checked against the type
expected, and never executed.

**Acceptance Criteria:**
1. Given a response larger than 5 MB, when it is read, then reading stops at 5 MB and the source fails with reason `invalid_content`.
2. Given a response whose content type is not a feed, HTML or JSON type the source's kind expects, when it is read, then it is not parsed and the source fails with reason `invalid_content`.
3. Given a feed with more than 200 items, when it is parsed, then the 200 newest are taken and the rest ignored.
4. Given an item whose title or summary contains HTML or script, when it is stored, then markup is stripped to text, control characters are removed, and the stored value contains no tag.
5. Given an item whose link is not `http` or `https` (`javascript:`, `data:`, `file:`), when it is parsed, then the item is rejected and counted under `rejected`.
6. Given XML with a DTD or an external entity, when it is parsed, then the DTD is not processed and no entity is resolved.
7. Given a compressed response that expands beyond 5 MB, when it is read, then reading stops at 5 MB of expanded content.

## L2-024: No requests to private or internal addresses
**Traces to:** L1-007

No request is ever sent to a loopback, private, link-local or cloud-metadata address, whether
reached directly, by redirect or by DNS rebinding.

**Acceptance Criteria:**
1. Given a source address whose host resolves to a loopback, link-local, private (RFC 1918), unique-local, multicast or cloud-metadata address, when it is added, tested or fetched, then no request is sent and the reason is `unsafe_address`.
2. Given a public address that redirects to a private one, when it is fetched, then the redirect is not followed and the reason is `unsafe_address`.
3. Given a host that resolves to a public address when checked and a private one when connected, when it is fetched, then the connection is made only to the address that was checked.
4. Given a chain of more than 5 redirects, or a redirect from `https` to `http`, when it is fetched, then it is not followed further and the source fails.
5. Given a URL with a user name or password in it, or a port other than 80 or 443, when it is added, then it is refused with `code` `validation_failed`.

## L2-025: API versioning and contract

## L2-033: API key authentication

2. Given a database behind the build's schema, when the API starts, then it does not migrate; it starts, reports not ready, and logs that `migrate` must be run.
3. Given `dotnet run --project src/Keryx.Cli -- migrate`, when it runs, then it applies pending migrations and exits `0`; run again, it changes nothing and exits `0`.
4. Given `… -- seed`, when it is run once or many times, then the regions, the categories, the default settings and the seeded news query sources exist exactly once each.
5. Given the worker starts against a database that is not ready, when it starts, then it runs no worker and reports not ready, rather than failing mid-run.
6. Given a shutdown signal during a run, when the worker stops, then the current source fetch is cancelled, the run is recorded as `failed` with reason `interrupted`, and the process exits within 30 seconds.

made, each one reversible by changing the requirement named. They replace the open questions in
the mocks' README.

| # | Question | Decision | Where |

| 1 | `AGENTS.md` speaks of events, organizations and churches; the mocks show articles only. | All three are records and all three are served by the API. | 4 | The mocks have no sign-in. | Staff sign in through an OpenID Connect identity provider; Keryx stores no password.
