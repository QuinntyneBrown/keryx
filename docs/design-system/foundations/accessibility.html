Accessibility

Overview

Keryx targets WCAG 2.2 level AA in both themes. Accessibility is built into the tokens and components, checked by script where it can be, and written down per component where it cannot. These are the system's commitments.

Perceivable

RequirementWCAGHow Keryx meets it
Text contrast1.4.3All text is at least 4.5:1 on every surface it sits on; pairs are declared and checked for both themes (colour).
Non-text contrast1.4.11Input edges, switch tracks, focus rings, status icons and chart marks are at least 3:1. Card edges, dividers and button outlines are decorative. Volt fills on light are decorative and always doubled by text.
Use of colour1.4.1Status is colour, icon and words; selection is fill and weight; links are underlined; invalid fields have an icon and a message.
Resize and reflow1.4.4, 1.4.10All sizes in rem; every screen reflows to 320 px with no sideways page scroll (tables and code scroll inside their own box).
Text spacing1.4.12No text in fixed-height boxes.
Non-text content1.1.1Decorative SVGs are aria-hidden; icon-only controls have aria-label; the logo has a name.
Motion2.3.3Reduced motion stops every transition and loop (motion).
Input purpose1.3.5autocomplete="email" on the alert address. Keryx collects no other personal data.

Operable

RequirementWCAGHow Keryx meets it
Keyboard2.1.1, 2.1.2Everything works with Tab, Enter, Space and, where a pattern says so, arrows. The only focus trap is a modal dialog, which Escape releases.
Focus visible2.4.7, 2.4.13One ring: 2 px, 2 px offset, on :focus-visible. Ink in light; volt in dark, in the sidebar, in the code panel and on toasts.
Focus not obscured2.4.11The top bar is not sticky; the save bar has 96 px of form padding beneath it; toasts ignore pointer events between them and are offset on Settings.
Focus order2.4.3DOM order is visual order; no positive tabindex; overlays move focus in and return it.
Target size2.5.8At least 24 × 24 px everywhere; 44 px on touch devices.
Dragging2.5.7The slider is the only draggable control and works with arrow keys.
Timing2.2.1Toasts last at least 8 s, pause on hover and focus; errors never auto-dismiss. A session that expires says so and returns the person to where they were.
Bypass blocks2.4.1A skip link on every page; landmarks for navigation and main.
Titles and headings2.4.2, 2.4.6A unique <title> and one h1 per page; headings in order.
Link purpose2.4.4Link text stands alone; new-tab links say so.

Understandable

RequirementWCAGHow Keryx meets it
Labels3.3.2A visible label on every control; placeholders are never labels; optional fields are marked, required ones are the default.
Error identification and suggestion3.3.1, 3.3.3Each error names the fix with an example; aria-invalid and aria-describedby; a summary links to each field and takes focus.
Error prevention3.3.4Destructive actions confirm in a dialog; reversible ones offer Undo.
Redundant entry3.3.7Entries survive a failed submit; edit dialogs are pre-filled.
Accessible authentication3.3.8Sign-in is delegated to the organisation's identity provider; Keryx shows no password field and no puzzle.
Consistency3.2.3, 3.2.4The same navigation in the same order on every screen; one meaning per icon; one word and tone per status.
On input3.2.2Changing a filter updates the list but never navigates or submits.
Language3.1.1lang on every page; aggregated titles use dir="auto".

Robust

RequirementWCAGHow Keryx meets it
Name, role, value4.1.2Native elements first; ARIA only to fill gaps, following the APG pattern named on each component page; overlays and menus come from the Angular CDK.
Status messages4.1.3Toasts, loading sentences, result counts and saved confirmations are in live regions: polite for information, assertive for errors.
Valid structure—No duplicate ids; no interactive element inside another; states that assistive technology must know are attributes (aria-current, aria-pressed, aria-invalid, disabled) and are styled through them.

The component contract

Every component page answers the same seven questions under Accessibility:

  1. Role and pattern. The element or APG pattern.
  2. Keyboard. Every key and what it does.
  3. Focus. Where it starts, where it returns, how it looks.
  4. Labelling. What is named, and how.
  5. Contrast. The pairs involved, live in both themes.
  6. Motion. What moves and what reduced motion does.
  7. Touch. Target sizes.

Aggregated content

  • Titles, descriptions, organisation names and error strings that came from a source are rendered as text, never as HTML.
  • A source link is rendered only if its scheme is http or https, and opens in a new tab with rel="noopener noreferrer".
  • Long and right-to-left titles are part of the Articles edge-case mock.

Testing

  • check_contrast.py: every declared pair, both themes.
  • check_design_system.py and check_mocks.py: labels, names, alt text, landmarks, headings, links.
  • Tab through each screen: the order is visual, the ring is always visible, nothing is unreachable.
  • Screen reader on one dialog, one form and one table.
  • Zoom to 200 % and 400 %.
  • Emulate prefers-reduced-motion, prefers-contrast: more and forced-colors.
  • On request: the Playwright accessibility sweep in frontend/e2e.
