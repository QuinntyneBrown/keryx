Components (59)

One page per BEM block. The page name is the block name and the name of the component's folder in frontend/projects/components/src/.

Actions

ButtonButtons start something: run the collector, save settings, add a source, revoke a key. One primary button per view says what the screen is for.Icon buttonA borderless square button for one familiar glyph: close a dialog, dismiss a toast, open the row menu.LinkLinks go somewhere: to another screen, to the run behind an issue, or out to the source that published an article.MenuA short list of actions for one row, opened from its ••• button.Segmented controlA row of two to five mutually exclusive options where all of them are visible and one is always chosen.

Inputs

Form fieldThe wrapper every control sits in: a label above, the control, then help or an error underneath.Text fieldA single line of text: a URL, a name, a number of seconds, an e-mail address. On a <textarea> the same block takes several lines.SelectOne choice from a list that is too long to show at once: a region, a category.Search field and toolbarA text field with a magnifier that filters the table under it, and the toolbar row it shares with the other filters.CheckboxZero or more choices from a short list, each with room for a line of explanation.Choice cards (radio group)A radio group drawn as a row of small cards, each with an icon: the type of a source.SwitchOne setting that is either on or off: include Ontario-wide organisations, alert when a whole run fails.SliderA value on a short scale where feeling the position matters more than typing a number: the relevance threshold.ChipA removable value in a list the person curates: the topics Keryx looks for, the terms it excludes, the areas it focuses on.Filter chipsA wrapping row of pills that narrows a table to one category: the type of a source.Settings section (form layout)The layout of a long form: a titled group with its explanation on the left and its fields on the right.Save barA bar that sticks to the bottom of the Settings page while there are unsaved changes, with the form's two actions.

Navigation

App shellThe frame every screen sits in: the ink sidebar, the main column, and optionally the article panel beside it.Sidebar and top barThe ink frame of the admin: the lockup, the six destinations, and the next collection. Below 1024 px the same block is the top bar.Navigation linkOne destination in the sidebar: an icon, a word, and sometimes a count of what needs attention there.Brand lockupThe Keryx mark and wordmark: a cross whose right arm lifts into a K, the herald raising a call.Page headerThe top of every screen: its name, one sentence of live context, and the screen's main action.Section headA heading for a block inside a page, with a link or a count at the other end of the row.TabsViews of one list by status, each with its count: All, Needs review, Published, Hidden.Pagination and table footerPrevious and Next under a table, beside the range of rows being shown.BreadcrumbThe path from a top-level screen down to the page in view. Keryx is flat today, so no mock uses it.Skip linkThe first focusable thing on every page: a link that jumps past the sidebar to the content.

Containers and overlays

CardA bordered white surface that groups one subject: a run's summary, the API's usage, the status of the pipeline.DialogA modal surface for one short task or one decision: add a source, create a key, confirm a removal.Detail panelThe article's details beside the table it came from: summary, provenance, why it is held, and the two things staff can do about it.TooltipA short label that appears on hover and on focus for a control or mark that has no visible text.DividerA hairline that separates two groups when space alone does not.Stack, cluster, rail and splitThe layout primitives that put space between components, so no component carries an outer margin.

Data display

TableRows of records with the same fields: articles, sources, API consumers. Real tables, so headers and cells are announced together.ListA bordered stack of rows for things that are read top to bottom: the latest articles, the run history, the issues in a run.Description listLabel and value pairs for one record: where an article came from, when it was collected, how it scored.AvatarA 28 px disc with the signed-in person's initials.BadgeA small pill that states a status or a count: Published, Needs review, 6.TagA small mono label for a machine name: the scope of an API key.HealthA dot and a short phrase that say how a source is doing: Healthy, Slow, 404 Not Found.StatA labelled number: 47 new articles, 62 of 64 sources, 84 ms.MeterA tiny bar and a two-decimal number for an article's relevance score.Source cellHow a source is identified in a row: a type icon in a tile, the organisation's name, and the address Keryx fetches.Status cardThe first thing on Overview: how the last collection went, its three headline numbers, and the last fourteen runs at a glance.Summary cardOne identifying value and three numbers about it: the API's base URL with its requests, latency and error rate.Issue cardOne open problem on Overview: what went wrong, for which source, since when. The whole card links to the run it belongs to.Run chartFourteen bars, one per run, showing how many new articles each brought in and which runs had trouble.TimelineThe steps of one run in order, each with its outcome, how long it took and what it produced.Endpoint rowOne API endpoint in the reference list: its method, its path and what it returns.Code panelAn ink panel with an example request and the response it returns.Copy fieldA value shown once in full with a button that copies it: a new API key.IconA 24-unit line glyph drawn in the text colour, at 14, 16 or 20 px.

Feedback

ToastA short message that confirms what just happened, in the corner, without taking focus: a source was added, a run finished, a key was copied.AlertA tinted message inside the page or a dialog, next to what it is about: why an article is held, what a test fetch found, why a save failed.CalloutA volt-tinted panel for the one moment that must not be missed: a new API key that will never be shown again.Progress barA thin volt bar that fills as the collector works through its sources.SpinnerA small turning ring for a wait of unknown length: a button that is submitting, a run that is collecting.SkeletonGrey shapes in the layout of the content that is about to arrive, so the screen does not jump when it does.Empty state and system pageWhat a screen shows when it has nothing to list, nothing matched, something failed, or the person cannot be here at all.

How to use

  • Read it. Before writing markup, find the component here. If it is missing, add it to the mocks and to this system first; never build a second component that duplicates or renames one.
  • Link the CSS for a static page or a mock: tokens/tokens.css then assets/components.css. The mocks in docs/mocks already do, through two one-line imports.
  • In Angular, tokens.css (with its @font-face rules and the bundled fonts) is a global foundation stylesheet. Each component in the components library gets its block's rules from components.css as its own encapsulated stylesheet, keeps the class names, and reads tokens by role.
  • Consume tokens elsewhere from tokens/tokens.json (Design Tokens Community Group format).
  • States are attributes (aria-current, aria-pressed, aria-invalid, aria-busy, disabled) and are styled through them. data-state exists only so static pages can show hover, focus and active.
  • Themes: press t or use the toggle in the sidebar; add ?theme=dark to any page.

Changing the system

  • A change starts in the mocks: add or change the state there, then update the token or component here, in the same change.
  • After any token change run the contrast check and regenerate tokens.json; after any page change run the structure check. All three commands are in the README.
  • Token names and page addresses are stable: rename nothing without updating the components library and the e2e page objects.
  • Record every corrected inconsistency in the README's drift log.
