Pattern

Feedback and loading

Which kind of feedback answers which event, and which loading indicator fits which wait.

WCAG 2.2 AAComposes components
  • Overview

  • Structure
  • States

Overview

Every action gets an answer, in the place the person is looking, at a volume that matches its importance. Every wait shows that something is happening and, when Keryx knows, how far along it is.

  • Feedback goes next to its cause when it has one, and in a toast when it does not.
  • Loading keeps the layout: skeletons have the shape of what is coming.
  • Nothing blocks the whole page except a dialog the person opened.

When to use

EventFeedback
A field value is wrongField error under the control (field)
A form could not be savedError summary at the top; danger alert for a server failure
A check inside a form finishedStatus alert in the form
An action succeededToast (success), or the save bar on Settings
A reversible action was doneToast with Undo, no confirmation first
A destructive action is requestedConfirmation dialog
A background run changed stateToast; the Overview status card and navigation badge update
A one-time value was createdCallout
A screen or area failed to loadError state in its place
A condition holds on a recordInline alert or badge
WaitIndicator
First load of a screen (over 300 ms)Skeleton in the real layout
An action in a button (under about 10 s)Busy button with a progress label
Work of known sizeProgress bar with numbers
Work of unknown length in a regionSpinner with a sentence
Next page of a tableBusy Next button; rows stay until replaced

Structure

Loading example

Started 9:46 AM · 38 of 64 sources checked

Test fetch found 6 event pages — 5 look relevant.
Skeleton for content, progress for measurable work, a busy button for an action, an alert for a result
  • Optimistic updates: Publish, Hide and Mute change the row at once and confirm with a toast; if the server refuses, the row reverts and a danger toast says so.
  • Undo lasts as long as its toast.
  • Skeleton delay: 300 ms, so fast responses do not flash.
  • Stale data: while a run is collecting, Overview keeps showing the last results and adds the progress bar.

States

PhaseShown
IdleContent.
Pending under 300 msNothing changes.
Pending over 300 msSkeletons, or a busy button; aria-busy on the region.
SuccessContent replaces skeletons without animation; a toast for actions.
EmptyAn empty state.
FailureAn error state or danger alert with a reference and Try again.
PartialWhat loaded, plus an alert naming what did not (the Overview partial mock).

Responsive behaviour

  • Skeleton layouts use the page's own responsive containers.
  • Toasts span the bottom of the screen below 640 px and dock bottom right above.
  • Progress bars and alerts are fluid.
  • A busy button keeps its width.

Accessibility

  • Loading regions have aria-busy="true" and one polite status sentence.
  • Results are announced: polite for success and information, assertive (role="alert") for failures (WCAG 4.1.3).
  • Progress has role="progressbar" with real values and a sentence updated at most every few seconds.
  • No feedback relies on colour alone.
  • Auto-dismissing feedback lasts at least 8 s and pauses; errors persist.

Content

  • Say what happened and what it means: “Saved at 9:46 AM. Keryx now collects every 3 hours.”
  • Failures say what was not lost.
  • Progress in numbers: “38 of 64 sources checked”.
  • Loading sentences name the screen.
