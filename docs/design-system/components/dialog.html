Dialog

A modal surface for one short task or one decision: add a source, create a key, confirm a removal.

Overview

Every edit in Keryx opens a dialog; there are no inline forms and no hand-rolled modals. A dialog asks for one thing, blocks the page behind it, and closes on Cancel, Close, Escape or success. Reading an article's details is not a task, so that uses the detail panel.

  • Form (512 px): fields, Cancel as a ghost button, one primary action.
  • Confirmation (416 px, .dialog__panel--sm): what will happen, Cancel as a default button with initial focus, and a danger-solid confirm.
  • Below 640 px every dialog is a bottom sheet.

Anatomy

  1. Backdrop--color-bg-backdrop over the whole page, which is inert.
  2. Panel--color-bg-surface-raised, --radius-xl, --shadow-4, at most 92 % of the viewport height.
  3. HeadTitle (--text-title), one-line description, Close.
  4. BodyFields or text, --space-4 apart; the only part that scrolls.
  5. FootRight-aligned actions above a hairline; the primary action last.

Sizes

Two widths.

Default · 512 px · --layout-dialog-widthSmall · 416 px · --layout-dialog-width-sm
Both are full width as a bottom sheet below 640 px.

States

A dialog moves through these states; each has a mock.

StateWhat changes
DefaultEmpty or pre-filled fields; first field focused (Cancel in a confirmation).
InvalidField errors under the controls; focus on the first invalid field; entries kept.
BusyFields and Cancel disabled, the primary button busy (“Adding…”), Close and Escape ignored.
TestedAdd a source only: a success alert with what the test fetch found.
FailedA danger alert at the top of the body with a reference; everything re-enabled; nothing lost.

  • On success the dialog closes and a toast confirms; the dialog never shows its own success screen.

Responsive behaviour

  • Below 640 px: a bottom sheet, full width, top corners rounded, sliding up; the foot stays visible while the body scrolls.
  • From 640 px: centred, 512 or 416 px wide, scaling in, with --space-6 around it.
  • The panel is never taller than 92 % of the dynamic viewport, so the on-screen keyboard does not hide the actions.
  • Footer buttons wrap, right-aligned, primary last.

Theming

The panel uses --color-bg-surface-raised: white in light, ink-850 in dark, which is two steps above the canvas so it reads as the top layer even though dark shadows are faint. The backdrop is 40 % ink in light and 65 % black in dark.

Accessibility

Role and pattern

The WAI-ARIA modal dialog pattern through the CDK Dialog: role="dialog", aria-modal="true", aria-labelledby the title, aria-describedby the description.

Keyboard

KeyAction
Tab / Shift+TabCycles through the dialog's controls only; focus is trapped.
EscCloses the dialog, unless it is busy.
EnterIn a field, submits the form.

Focus

On open, focus moves to the first field, or to Cancel in a destructive confirmation. On close it returns to the control that opened the dialog; if that control is gone (a removed row), to the table. Close the dialog by its ref before navigating.

Labelling

The title names the task or asks the question (“Remove Redeemed Run Club Toronto?”). Close is labelled “Close”.

Motion

The backdrop fades in over --duration-base; the panel scales in from 0.96 (slides up 8 px as a sheet) over --duration-slow. Both are instant under reduced motion.

Touch

Buttons and Close are 44 px on touch. The sheet has no drag handle; it closes with Cancel or Close.

Content

  • The title is the task (“Add a source”, “New API key”) or, for a confirmation, a question naming the thing.
  • The description says what happens next in one line: “Keryx will check it on every scheduled run.”
  • A confirmation body says what is kept and what is lost, and whether it can be undone.
  • The confirm button repeats the verb and object of the title: “Remove source”, “Revoke key”.
